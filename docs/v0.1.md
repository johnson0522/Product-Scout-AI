# Product Scout AI V0.1

## 1. Objective

Validate whether an Agent can perform useful product discovery research from a natural language product goal.

---

## 2. Example Input

```json
{
  "goal": "寻找适合美国小企业的 AI SaaS",
  "constraints": {
    "market": "US",
    "price": "$20-$100/month",
    "competition": "low"
  }
}
```

The system should produce:

### Market Summary
* target market
* target users
* market context
* important trends

### Pain Points
For each pain point:
* description
* affected users
* frequency
* evidence
* confidence

### Competitors
For each competitor:
* product
* target users
* pricing
* core features
* positioning
* customer complaints
* weaknesses

### Market Signals
* trends
* new products
* funding
* search interest
* community discussions
* regulatory or technology changes

### Opportunities
Each opportunity contains:
* title
* target customer
* problem
* evidence
* solution
* why now
* monetization
* MVP
* score
* confidence

Day 1:

Early users

## Evidence Store Status

V0.1-C2-B provides create and get-by-id persistence for the C2 Evidence
model through `EvidenceRepository` and `DrizzleEvidenceStoreRepository`.
SearchResult to Evidence conversion was outside C2-B; claim persistence remains
outside V0.1-C2-C.

## Search Result Evidence Integration Status

V0.1-C2-C maps the existing SearchTool result items to validated Evidence and
persists each valid item through EvidenceRepository. IDs are generated at the
application boundary, retrieval time is captured for each mapping attempt,
and repeated collection creates a new Evidence rather than deduplicating by
URL. Per-item mapping or persistence failures do not stop later items and are
returned with distinct statuses. Unit tests use mock search/repository
boundaries; real PostgreSQL integration remains pending a test-only database.

## Evidence to Research Finding Status

V0.1-D1 adds the traceable chain Evidence to Claim to Research Finding.
Claims require one or more unique Evidence references, and Findings require one
or more unique Claim references. The application service rejects missing
Evidence, missing Claims, and Claims from a different ResearchRun before any
aggregate is persisted. A stored Finding can be resolved through its Claims to
the original Evidence source URLs.

Claim and Finding aggregates are persisted in normalized PostgreSQL tables by
transactional Drizzle repositories. The migration does not change the legacy
evidence table or existing evidence_store columns, and D1 does not add
confidence weighting, contradiction resolution, Agent Runtime behavior, or
new product events.

## Research Quality Control Status

V0.1-D2 adds deterministic, explainable quality checks for an existing D1
Research Finding trace. Callers explicitly provide Evidence semantic/source
classifications and the Evidence-to-Claim relationship; the system does not
automatically generate Claims or infer that an Evidence reference supports a
Claim.

The current rules detect unassessed relationships, Claims without supporting
Evidence, single or duplicated source URLs, incomplete Evidence
classifications, strong universal Claim wording with limited source diversity,
and simultaneous supporting and contradicting relations. Simultaneous
relations are reported as conflict candidates requiring human review, not as
automatic factual contradiction decisions.

Quality results expose status, rule IDs, reasons, affected Claim/Evidence IDs,
source URLs, blocking severity, and human-review requirements. They are
calculated on demand and are not persisted. D2 does not modify database schema,
the D1 aggregate contracts, Agent execution, Product Events, or SSE.

## Research Workflow Contract Status

V0.1-D3-A defines the minimum application-layer contract for a future research
workflow. It fixes the six-step dependency graph, validates workflow inputs,
defines workflow and step statuses, models typed failure categories, and
expresses bounded explicit retry semantics.

V0.1-D3-B adds a minimal in-process `InMemoryResearchWorkflowCoordinator`.
Step handlers are injected, and the current implementation uses deterministic
Fake handlers for application-layer execution tests. It verifies dependencies,
tracks step attempts and results in memory, stops after a failed step, marks
downstream pending steps as skipped, and supports cooperative cancellation.

V0.1-D3-C connects the first four workflow steps to Search and Evidence
Ingestion. At that phase boundary, opportunity analysis and report generation
still stopped explicitly.

V0.1-D3-D-B adds successful Evidence acquisition records. Canonical Evidence
remains in `evidence_store`, while `evidence_acquisitions` records the
ResearchRun, workflow invocation, step, source fingerprint, and capture time.
Scoped replay is idempotent, but identical URLs are not globally deduplicated.
Evidence reuse across ResearchRuns is explicit. Claim creation now requires an
Evidence acquisition for the Claim's ResearchRun.

V0.1-D3-E-B adds an explicit `ResearchSynthesisPlanProvider` boundary for the
opportunity-analysis workflow step. An injected provider supplies Claim and
Finding drafts together with explicit Evidence relationships and
classifications. The application validates all references against typed
Evidence artifacts from completed search steps, persists or reuses Claims and
Findings deterministically, and immediately evaluates each Finding with the D2
quality service. It never treats an excerpt as a Claim or assumes a supporting
relationship.

The analysis step now emits typed Finding and Quality artifacts. Insufficient
or conflicted research remains a technically completed analysis with blocking
or human-review diagnostics. This phase does not include a production LLM/DSH
synthesis provider, Opportunity aggregate generation, scoring, report
generation, or quality-result persistence. Report generation therefore still
stops explicitly.

The coordinator still does not add durable workflow persistence, queues,
schedulers, distributed coordination, automatic retries, or exactly-once
workflow execution. AgentRuntime and DSH integration remain separate.

## Analysis Workflow Runtime Status

V0.1-D3-E-C implements the production-capable DSH synthesis boundary through
`AgentRuntimeReasoner` and a schema-validated submission Tool. Assistant prose
is not parsed as a business result, DSH stays pinned to `0.2.1-alpha.1`, and
default tests do not require a model API key.

V0.1-D3-E-D introduces the separately versioned
`product-scout-analysis-v0.1` workflow and adapts it to `AgentRuntime`. The
analysis workflow ends after Finding and Quality artifacts and may complete at
that boundary. The full `product-scout-research-v0.1` workflow still requires
Report generation and must fail when that required step is absent.

The dependency-injected analysis composition reuses the real Search, Evidence
acquisition, Finding, Quality, and synthesis services. Cancellation uses a
shared ResearchRun/workflow invocation identity to mark the Coordinator and
close an active Reasoner request. The Web production Gateway has not switched
to this analysis-only runtime, so `POST /api/research` does not yet claim this
partial workflow as a full V0.1 ResearchRun.

## Opportunity Scoring Contract Status

V0.1-D3-F-A adds an injectable `OpportunityAnalysisPlanProvider` and a pure
`OpportunityAnalysisService`. A plan references existing Findings and provides
all seven scoring inputs with explicit explanations. Product Scout rejects
unknown or duplicate Finding references, Findings that have not passed the D2
quality gate, invalid scores, empty explanations, malformed fields, and
model-supplied total scores.

Evidence references are derived from accepted Findings rather than copied from
provider output. The weighted total is always calculated by the existing domain
`calculateOpportunityScore` function, so equal inputs produce equal scores. An
empty Opportunity result is valid when the available evidence does not justify
a product conclusion.

D3-F-A does not persist Opportunity records or score explanations, register a
DSH Tool, modify the opportunity-analysis Workflow handler, generate Reports,
or create Validation Plans. Those integration and persistence decisions remain
explicit follow-up work.

## Production Workflow Status

V0.1-D3-G-A switches the production Web Gateway from the echo-only DSH PoC to
`product-scout-research-v0.1`. The Product Layer still talks only to
`AgentRuntime`; concrete DSH reasoners are assembled inside `apps/agent` and
receive explicit Search and persistence ports.

A production ResearchRun can now complete only after all six steps and both
final persisted artifacts succeed. Missing configuration, Search failure,
invalid structured model output, persistence failure, cancellation, or the
overall workflow timeout results in a failed or cancelled run rather than a
false completion.

This phase does not add Report/Evidence/ValidationPlan read APIs or UI. Product
events are durable, but the current Gateway publishes the returned trajectory
after runtime completion; truly incremental live delivery remains outstanding.

V0.1-D3-G-B adds an optional awaited runtime event sink and projects Workflow
step transitions into both durable Product Events and `research_steps`.
Incremental and final trajectory delivery are deduplicated by event ID.
ResearchStep IDs are deterministic per ResearchRun and step type, so a retry
updates the same business record rather than storing runtime trajectory.

`POST /api/research` now returns `201` with the ResearchRun ID immediately after
creation and starts execution in the current process. Clients can then attach
to the existing SSE endpoint and replay any events persisted before the
subscription. The process-local execution model still does not provide restart
recovery, queues, workers, or exactly-once guarantees.

## Local V0.1 Completion Status

Project creation/history, Research read APIs, reports, explained scores, MVPs,
seven-day plans, Evidence trace views, live SSE progress, cancellation, bounded
public-HTTPS fetching, and Source persistence are now connected. Constraints
are propagated through Search and structured reasoning. Cancellation and terminal
ordering are protected within the process-local Gateway.

The current acceptance target is a local single-owner evaluation workspace;
authentication and remote/multi-user hosting are not implicitly provided. No new
migration or DSH upgrade is introduced by this completion phase.

Real PostgreSQL integration, browser contract checks, live Search and live Fetch
are recorded separately from live DSH/model research acceptance. Missing model
credentials prevent a claim that all V0.1 acceptance criteria have been proven
with real research. See `v0.1-acceptance.md` for the AC-01–AC-15 matrix and startup
requirements. Historical phase sections above retain their original scope.

Finding quality diagnostics are now saved by Finding/invocation/rules version
and displayed through the existing Evidence API and Research workspace.
Snapshots retain classification inputs and deterministic rule outcomes, not
runtime trajectory. Older runs without snapshots are explicitly unrecorded.
Migration 0008 is required; `rqc-v1` and the report gate are unchanged. See
`research-quality-diagnostics.md` and ADR-014.
